  save correctly. This also settled OPEN-QUESTIONS #4 (WP §4.5): the API now
  refuses rows with both, while the DB constraint stays relaxed for any

## 2. Phase 3 — Excel import/export (done + deployed)

- **All seven import types** from the prototype: employees, projects,
  departments, standard hours, attendance (Lumen), repairs, and bulk
  historical reports. The parsers are ported from the prototype — the thing
  that already works against the company's real files — not from WP §9.1's
  column table (which the prototype provably contradicts).
- **Preview-then-commit**: choosing a file shows new / updated / unchanged
  counts plus per-row errors *with Excel row numbers*; nothing is written
  until confirmed. Re-importing the same file changes nothing (idempotent,
  WP §9.2). Commit re-posts the same file, so the server stays stateless.
- **Merge-semantics updates**: re-importing employees never clobbers target
  hours; departments never lose their bucket mapping.
- **FK-safe**: a standard-hours box referencing a missing parent project, or
  an attendance row for an unknown employee, becomes a row error with advice
  ("load the projects file first") instead of failing the whole import.
- **Exports** on the reporting grid, archive, and activity log — the
  prototype's exact Hebrew headers and file names, honoring on-screen filters.

## 3. Phase 4 — Analytics (done + deployed)

- **Attendance cross-check**: one row per active employee, least-covered
  first; reported vs clock hours, variance beyond ±1h flagged red (WP §5.5);
  clock hours editable inline (manager+). Reads the same database function as
  the grid's status dots, so the two screens cannot disagree.
- **Dashboard**: KPI cards (total hours, productive/overhead ratio, overruns,
  savings), budget-vs-actual per project with variance pills and utilization
  bars, and hours-by-bucket chart. Filterable by day / last week / month / all
  and by customer. Projects with reported hours but no standard are shown as a
  count instead of silently dropped (WP §6.4 acceptance).
- All aggregation runs in the four database functions deployed with the
  schema; the route only resolves the period selection.
