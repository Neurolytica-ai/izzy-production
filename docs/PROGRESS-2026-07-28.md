## Findings that need client decisions

These were found by checking the prototype's data rather than trusting the
document. Each is recorded in full in `docs/OPEN-QUESTIONS.md`.

### 1. 14,146 standard hours are invisible to budget control

66 of the 159 box definitions roll up to a parent project that does not exist —
43 distinct missing project numbers. The prototype hides this completely: its
dashboard only lists projects present in both tables, so these boxes and their
costed hours silently never appear in any planned-vs-actual comparison.

**Needed:** are these missing projects that should be created, or dead rows to
delete? Until then the system tolerates them and reports them rather than
blocking the data migration.

### 2. A department name contains a double space

The prototype maps `"חשמל  סולארי"` (two spaces) to the electrical bucket, and no
department by that name exists. If the real Excel spells it with one space, those
hours resolve to no bucket and disappear from the dashboard chart with no error.
The new system matches whitespace-insensitively so it cannot lose the hours, but
the source data should still be corrected.

### 3. "Submit day to archive" does not archive anything

WP §7.3 describes it as committing a day's draft rows. In the prototype there is
no draft state — rows are saved as they are typed — and the action only sets a
marker and moves to the next day.

**Needed:** should submitting *lock* the day against further edits, or stay a
marker? Built as a marker for now; a lock is additive later, whereas removing a
lock nobody wanted is not.

### 4. The Excel column mappings in WP §9.1 do not match the working prototype

The prototype's parsers are what actually work against the customer's files, and
they differ materially: the customer name is derived from the project name rather
than read from a `לקוח` column, the subcontractor is pattern-matched from the
employee name rather than read from a `קבלן` column, and several headers differ
(`פוליאוריתן` not `הזרקה`, `הדבקות` plural). This is why the real files are needed.

### 5. Nine boxes where the total does not equal the sum of its ten buckets

For example box 24399. Stored exactly as given — the sheet's total is treated as
authoritative and nothing is silently corrected — but worth confirming.

### 6. Security: credentials in circulation

WP §10.1 contains a shared root password for the target server in plain text, in a
document that has been distributed. **It should be rotated regardless of go-live
timing.** Nothing in this project has connected to that server.

## Technical decisions taken

| Decision | Reason |
| --- | --- |
| Supabase (managed PostgreSQL) | Customer preference (WP §3.2); its automated backups also satisfy WP §10.4, which the plan calls a launch blocker |
| React 19 + TypeScript + Vite | Customer request. Recorded trade-off: rewriting the hours grid is the most expensive work in the project |
| WP §5 rules implemented as SQL functions | One definition each, so the API and the dashboard cannot disagree about them |
| Exact decimal hours (`numeric`) | The prototype compares hours with a floating-point tolerance; exact decimals remove the need |
| Derived fields resolved server-side | The client can never invent a project number, and unresolvable input is refused rather than stored |
| English interface for now, Hebrew catalogue shipped alongside | Development speed. **Production must switch to Hebrew before go-live** — one setting, no retranslation |
| Audit log stores stable codes, not display text | The prototype wrote Hebrew text into its log, which makes it unfilterable by action type |
| No default account | Shipped default credentials are the usual way an internal tool becomes publicly writable |

Two behaviours were reproduced from the prototype that the work plan does not
document at all: the confirmation prompt when a day's hours exceed an employee's
target, and the fact that editing a day already over target does not re-prompt.
